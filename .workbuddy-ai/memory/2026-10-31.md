## 追加：整体性能瓶颈分析（docs/performance-analysis.md）
- 新增 `docs/performance-analysis.md`（9 条瓶颈，P0/P1/P2 + 目标/验证/风险）与 `scripts/perf-baseline.py`（合成数据微基准，开发用不打包）。
- 实测（本机，非微信真实库）：单行 SQLite 提交 8.8ms（journal=delete/sync=FULL），100 行单事务 0.14ms/行（63×）；
  contact 全表 1k=15ms / 5k=68ms / 20k=290ms，且 `_contacts` 无缓存、messages/sessions/history_page/profile_metadata 每请求都读；
  画像 state 5000 条 = 36KB / json.loads 0.61ms；tsx 启动比 node 多 220ms。
- 关键代码事实（易记错）：
  - `_run_visible_priority` 有 batch_engine 时转 `_run_fine_recent`，**每条消息 1 次 session.run（rows=3）**，fine 题集只有 3 题；
    历史/画像打包路径 `analyzeMessageBatch` 每窗口 4–6 次 run（13 题按 BATCH_SIZE=8 拆 2 次 + 级联 detail），单条成本是 fine 的 1/1.5~1/5。
  - `/api/messages` 一次触发 2–3 次 fresh 身份校验（`_scoped_identity` + `_ordinary_db` + 助手启用时的 `_check_identity(fresh=True)`），
    RM 查询注释自述「数百 ms」，`_live_reader_valid` 还会读每个分片首页并做 HMAC。
  - 已排除的非瓶颈：tokenizer/prefix ≤0.4ms、JSON.stringify 80 条 0.16ms、jieba 0.1ms、ResultStore 建表 9–16ms。
- 基线陷阱：`ResultStore.save()` 对已存在 id 会提前 return，基准里重复用同一批 id 会测出 0.9ms 的假象，必须每次换新 id。
